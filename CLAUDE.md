# Steam Controller Toolkit

A cross-platform desktop app (Windows, macOS, Linux) for tinkering with the **2026 Steam Controller**
(codename "Triton"). Each tool lives in its own tab: Visualizer (live input), Haptics (play every haptic
effect), MIDI (controller as a MIDI controller), Raw data (device facts and report bytes), Recorder (record and replay reports) and About (credits). The look follows `mockups/redesign.html` ("Big Picture"): dark
navy, Barlow (bundled via `@fontsource/barlow`), Steam blue `#1a9fff`, rounded tiles; the tabs are in a
left sidebar (`mockups/sidebar.html`, Panel style).

Branding: logo master is `assets/logo.png` (1024px); app icons in `src-tauri/icons/` are
generated from it with `npx tauri icon assets/logo.png` (delete the android/ios folders after);
`public/logo.png` is the in-app/favicon copy. Code is MIT (`LICENSE`); the protocol is
documented for humans in `docs/PROTOCOL.md`; keep it in sync with `protocol.rs`. The README
links the demo video (YouTube `QCvgsTT6-FI`) and shows one screenshot per tab from
`docs/screenshots/` (taken at the default 1280 x 720 window, 1.5x); retake them when a tab's look changes
with `tools/screenshots` (the real UI fed a real recording through a mock backend, captured by headless
Edge/Chrome; see its README). The MIDI tab has two shots: `midi.png` and `midi-guide.png`.

Versioning: semver, `package.json` is the single source (`tauri.conf.json` points at it,
`tools/sync-version.mjs` copies it to `src-tauri/Cargo.toml` + `Cargo.lock` as npm's `version` script).
Every user-visible change gets a line in `CHANGELOG.md` under the next version; releasing is
`npm version minor|patch` then `git push --follow-tags` (see README, Releasing). Never push tags
without the user asking: a `v*` tag makes CI draft a release.

## Stack

- **Tauri 2**: Rust backend + vanilla TypeScript/Vite frontend (no framework).
- **`crates/sc-core`**: the device layer, independent of Tauri. Discovery, configuration, report
  parsing, and the `hub` that runs one reader thread per HID interface with hot-plug.
- **`src-tauri`**: starts the hub, folds reports into a `Snapshot`, and emits it to the UI as the
  `controller` event at ~60 Hz (the controller itself reports at ~265 Hz).
- **Recorder**: `sc_core::recording` is the `.screc` file format (text: header line, then
  `<seconds> <slot> <hex bytes>` per report). `src-tauri/src/tape.rs` writes every live packet
  while recording and replays a file with its original timing. `forward_events` keeps two folds,
  live and replay, and emits the replay one while a recording plays, so every tab shows it
  unchanged; `Snapshot.tape` says what is recording/playing. Files live in
  `<app data dir>/recordings` (not Documents: macOS would prompt for access). During playback
  the power button is hidden and Haptics acts disconnected.
- **MIDI**: `src-tauri/src/midi.rs` is the engine, pure and unit-tested: a `Preset` of
  `Mapping`s (source string -> shaping -> `Target` message) plus a `PadGrid` per trackpad;
  `Engine::process` turns each state report into messages, sent only when the value they carry
  changes. `midi_out.rs` owns the port (`midir`), `config.json` and saved presets in
  `<app data dir>/midi`, and the `MidiStatus` in `Snapshot.midi`. `forward_events` feeds it every
  state report (~265 Hz, not the 60 Hz UI rate) from whatever the UI shows, live or replay, and
  releases held notes when switching between them, seeking, or losing the controller. Ports open
  on a thread of their own (`tick` picks up the result), never on the event loop. macOS (CoreMIDI)
  and Linux (ALSA) get a virtual "Steam Controller" port from midir; not yet run on those systems,
  only built in CI. Windows gets one from Windows MIDI Services (`midi_win.rs`, app-to-app MIDI)
  on 11 25H2+, else the user picks a loopback port (loopMIDI). The MIDI tab's Setup guide is
  per system (`guideHtml`/`portStep` in `src/tabs/midi.ts`); keep it in step with the README.
  Source names are mirrored in `SOURCES` in
  `src/tabs/midi.ts` and the presets' JSON shape in `controller.ts`; keep them in sync. Learn
  (`Engine::start_learn`) ignores touch sensors and gyro, which move whenever anything else does.
  Other outputs (OSC, virtual gamepad, keyboard/mouse) should hang off the same feed.
- **Windows MIDI Services** (`midi_win.rs`): the API is a preview until Windows ships it (late
  Nov 2026). We embed Microsoft's preview `Windows.Devices.Midi2.dll` + `.pri`
  (`src-tauri/vendor/windows-midi-services`, extracted to `<app data>/midi/windows-midi-services/<PREVIEW>`
  and loaded only if Windows has no copy). Bindings are generated by `tools/midi2-bindings`
  (windows-bindgen 0.100 + `fix.py`; see its README); never hand-edit `midi2_bindings.rs`.
  `Support::System` (Windows' copy) is a normal, default output. `Support::Preview` (ours) is
  opt-in "experimental": verified on 25H2 in Oct 2026, today's service makes ONE virtual device
  per `midisrv` run; a second `CreateVirtualDevice` hangs until the service restarts (closing
  or a new product id doesn't help). So the port is made at most once per app run and kept
  until exit, every service call has a timeout, and first-run defaults never pick it. Testing
  it: `cargo test -p steam-controller-app --lib virtual_port -- --ignored --nocapture`, once per
  service restart (restarting `midisrv` needs admin; a stuck one must be killed). Microsoft's
  go-live terms: never on Windows below 25H2, keep up with previews, tell users it's a preview,
  remove our copy once Windows has it.
- **`src/`**: `main.ts` builds the sidebar from the `tabs` array (grouped by `group`); each tab implements `Tab` in
  `src/tabs/tab.ts`. `src/controller.ts` mirrors the Rust types and must be kept in sync with
  `crates/sc-core/src/protocol.rs` and `Snapshot` in `src-tauri/src/lib.rs`.

## Adding a tab

Create `src/tabs/<name>.ts` implementing `Tab` (with a `group` and an icon in `src/tabs/icons.ts`),
add it to the `tabs` array in `src/main.ts`.
If it needs data the snapshot lacks, extend `Snapshot` in Rust and `controller.ts` together.
If it needs to send commands to the controller (haptics, settings), add a method on
`sc_core::Controller`, a `hub::Command` variant that `read_loop` runs, and a Tauri command in
`src-tauri/src/lib.rs` that sends it with `Hub::send` (see `turn_off_controller`).

## Protocol notes (verified on hardware)

Reference implementation: SDL `src/joystick/hidapi/SDL_hidapi_steam_triton.c` and
`steam/controller_structs.h`. Little-endian, packed.

- VID `0x28DE`. PIDs: `0x1302` wired, `0x1303` BLE, `0x1304` "Steam Controller Puck" wireless
  dongle, `0x1305` newer dongle. Dongle interfaces 2..=5 are four controller slots.
- On Windows each interface splits into mouse / keyboard / vendor (usage page `0xFF00`)
  collections; only the vendor one carries reports.
- Feature report `[0x01, 0x87, len, (setting u8, value u16)...]` sets settings. We send
  lizard mode (9) = 0 and IMU mode (48) = raw accel|gyro (0x18), re-sent every 2 s because the
  controller reverts. It fails on empty dongle slots, which is expected.
- Power off: feature report `[0x01, 0x9F, 4, 'o','f','f','!']` (`ID_TURN_OFF_CONTROLLER`, payload
  from the original Steam Controller), sent via `Hub::send(slot, Command::TurnOff)`. SDL's Triton
  driver never uses it, but it works on this controller (verified over the Puck dongle).
- Haptics: output reports `0x80`..`0x85` (rumble, pulse, built-in effect, tone, sweep, script;
  `protocol::Haptic`), sent with `Hub::send(slot, Command::Haptic { .. })`. All verified on
  hardware. `side` is 0 left, 1 right, 2 both (3+ = nothing; test with a thumb on each
  trackpad, not by the grips). Effects 0x82 only play tick/click; scripts 18+ are empty. A rumble stops ~50 ms
  after the last report, so `read_loop` resends it every 40 ms until both speeds are 0.
  `cargo run -p sc-core --example haptics [-- --buzz N click]` tests them.
- Input report `0x42` (54 bytes, includes orientation quaternion) observed at ~265 Hz.
  `0x45` has no quaternion, `0x47` adds a trackpad timestamp. `0x43` battery, `0x79`/`0x46`
  wireless connect/disconnect. `0x7b` seen but undecoded.
- Accel 16384 counts = 1 g. Gyro ±2000 °/s full scale.
- Reading works while Steam is running. But Steam's Desktop Layout then turns the controller
  into mouse/keyboard input on its own, which our lizard-mode-off cannot stop (it only stops
  the firmware's emulation). The app detects Steam (`watch_steam` in `src-tauri/src/lib.rs`)
  and shows a warning banner.
- Never poll several interfaces in turn with short timeouts: Windows timeouts are ≥ ~15 ms and
  you lose ~90% of reports. Use one blocking thread per interface (see `hub.rs`).
- Only send settings to a slot after it has sent a state report (as SDL does). Sending them to
  empty dongle slots fails every time.
- Report `0x42` carries an orientation quaternion (w, x, y, z; 32767 = 1.0) that rotates sensor
  vectors into a world frame with +Z up. Sensor frame: +X right, +Y forward (towards triggers),
  +Z out of the face. Three.js mapping is (x, y, z) -> (x, z, -y). Yaw drifts / has no absolute
  reference; the visualizer's Re-center yaw button zeroes it for the angle readout.
- The 3D view rests front-facing. While the right trigger is pulled past 30% it follows how the
  controller has turned since the pull, in the controller's own frame: `FRONT * grab⁻¹ * current`
  (the pose at the pull becomes the resting pose; no heading needed, which the IMU cannot give). It eases
  back on release (`Controller3D.rotating`). The hint pill in the view says so; keep it.

## 3D model

`public/models/steam-controller.glb` is adapted from "Steam Machine + Controller" by
dark_igorek (Sketchfab, CC BY 4.0). **Attribution is a license requirement**: keep the credit
in the About tab (`src/tabs/about.ts`), `public/models/README.md` + `LICENSE.txt`, and the README credits, and
credit dark_igorek anywhere the model is shown or shipped (about screens, store pages, docs).

Regenerate with
`node tools/convert-model.mjs <steam_machine__controller.glb> public/models/steam-controller.glb`.
The script splits the controller's details mesh into connected pieces and names them
`part_<name>` (matched by position via `PARTS`); `controller3d.ts` gives each a pivot and
moves it from live input. The D-pad is then cut along its diagonals into `part_dpad_up/down/left/right`
by headless Blender (`tools/split-dpad.py`; found via `$BLENDER`, the default install paths or
PATH), so each arm lights up on its own; the arms share one pivot and tilt together as a rocker. Keep it light: one model, 1024px WebP textures, on-demand rendering
(draws only when orientation/inputs change), pixel ratio capped at 1.5, nothing drawn while the
window is hidden. Append `#demo` to the page URL to cycle every input in the 3D view (it replaces a connected
controller's inputs; the view only updates while a controller sends state reports).

## HID enumeration must stay filtered

Never enumerate all HID devices (`HidApi::new()` with discovery on, `refresh_devices()`,
`add_devices(0, 0)`). On Windows, hidapi asks every matching device for its strings, and some
devices never answer (seen: Corsair `1b1c:1b3a` hangs in `HidD_GetSerialNumberString`), which
blocks forever. Use `device::valve_api()` / `device::rescan()`, which only enumerate VID 28de.
`third_party/hidapi` is hidapi 2.6.7 patched so `HidApi::new()` honours
`disable_device_discovery()`; it is wired in via `[patch.crates-io]` in the root `Cargo.toml`.

## Commands

- `npm run tauri dev`: run the app
- `npm run probe -- --raw --seconds 10`: terminal dump of devices and live decoded reports
- `npm run tauri build`: release bundle for the current OS (macOS/Linux builds need those OSes; use CI)
- CI (`.github/workflows/build.yml`, tauri-action): run it by hand for Windows/macOS (universal)/Linux
  bundles as run artifacts; pushing a `v*` tag also puts them in a draft GitHub release. Each OS
  also gets a portable build that runs without installing: the bare `.exe` (frontend is embedded),
  the zipped `.app`, the AppImage

## Platform notes

- Linux needs udev rules granting access to `hidraw` for VID 28de (Steam installs them).
  Building on Linux needs `libasound2-dev` for `midir` (installed in CI).
- Windows: the app's own MIDI port needs Windows 11 25H2+ (see Windows MIDI Services above).
- macOS may prompt for Input Monitoring permission.
- The window opens at 1280 x 720 and has a minimum size of 960 x 640 (`tauri.conf.json`); every tab
  must fit without horizontal scrolling. Tabs sit in a grouped sidebar (`Tab.group`, `Tab.icon` from
  `src/tabs/icons.ts`): 208 px with names from 1100 px wide, a 68 px icon rail below that or when
  collapsed (remembered in localStorage). So the tabs get as little as ~850 px (1100 px with names);
  size tab layouts with `@container tab` (`#tab-content`), not the window width. The MIDI tab has a
  narrower layout for that (`@container tab (max-width: 900px)`). Check new tabs at 1100 and 960 px.
  Tabs scroll vertically if needed, with the themed thin scrollbars.
